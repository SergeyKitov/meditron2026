# Запуск Patient pathway

**Актуально на 05.10.2026:** рабочий проект следующего шага строит CatBoost после детерминированного разбора полей. Артефакт модели включён в `config/model/`; воспроизводимое обучение на синтетике: `.venv/bin/python scripts/train_route_model.py`. Правки специалиста пока сохраняются для последующей экспертной разметки и пакетного переобучения. Демонстрационный переключатель профилей в верхней панели не является системой авторизации.

Проект запускается как локальное **синтетическое демо**. Имена, заключения, DICOM SR, запись и уведомления в нём демонстрационные. Предложения модели имеют статус `HYPOTHESIS`; каждый проект пути должен подтвердить специалист до показа пациенту.

## Запуск на компьютере

Из корня проекта нужны Python 3.12 или 3.13, [uv](https://docs.astral.sh/uv/getting-started/installation/), Node.js 20.18+ и npm. Проверить версии можно командами `python3 --version`, `uv --version`, `node --version`, `npm --version`.

```bash
uv sync --frozen
npm --prefix frontend ci
bash scripts/dev.sh
```

Откройте интерфейс: <http://127.0.0.1:5173/>. Документация API: <http://127.0.0.1:8000/docs>. Проверка API: <http://127.0.0.1:8000/health>.

`scripts/dev.sh` сначала проверяет, что порты свободны, затем для стандартной локальной `meditron.db` **удаляет предыдущие случаи и создаёт девять новых пациентов**, применяет миграции и запускает API, обработчик фоновых событий и веб-интерфейс. Адрес печатается только после ответа API и страницы с заголовком **Patient pathway**. В строке запуска виден абсолютный каталог проекта: проверьте, что это нужная рабочая копия. Если случаи нужно сохранить для отладки, запустите `MEDITRON_DEMO_RESET=0 bash scripts/dev.sh`. Базы с другим `DATABASE_URL` автоматически не очищаются. Остановите процессы нажатием `Ctrl+C` в терминале с запущенным скриптом.

Локальный запуск проверен на отдельной SQLite базе: главная страница, `/health` и `/docs` ответили HTTP 200. Установка зависимостей с нуля на этой машине не повторялась: проверка использовала уже подготовленные `.venv` и `frontend/node_modules`.

Если стандартные порты заняты, задайте оба до запуска:

```bash
MEDITRON_API_PORT=8100 MEDITRON_WEB_PORT=5183 bash scripts/dev.sh
```

В этом случае интерфейс открыт на `http://127.0.0.1:5183/`, а API — на `http://127.0.0.1:8100/docs`. Для отдельной демонстрационной базы можно задать `DATABASE_URL=sqlite:////absolute/path/to/demo.db`.

## Если открывается прежний вариант

1. Проверьте адрес страницы: локальный запуск выше открывается на `http://127.0.0.1:5173/`. Старую вкладку на другом порту или опубликованный сайт легко принять за новую сборку. В свежей версии заголовок вкладки — **Patient pathway**, а сверху есть переключатель трёх профилей.
2. Проверьте каталог в сообщении `Patient pathway из ...` и запустите именно `bash scripts/dev.sh` из этого проекта. `npm --prefix frontend run dev` запускает только интерфейс и может обращаться к старому API на порту 8000.
3. Если порт занят, новый `dev.sh` завершается с явной ошибкой, вместо того чтобы оставить вас на странице прежнего сервера. Посмотрите владельца порта: `lsof -nP -iTCP:5173 -sTCP:LISTEN` и `lsof -nP -iTCP:8000 -sTCP:LISTEN`. Остановите свой прежний терминал через `Ctrl+C`. Если это ваш контейнер этого проекта, выполните `docker compose down` в каталоге проекта. Можно также выбрать отдельные порты командой выше.
4. Если запускали Docker, пересоберите образы после изменений исходников: `docker compose up --build --force-recreate`. Обычный `docker compose up` может использовать уже собранный веб-образ со старым интерфейсом.
5. После подтверждённого запуска обновите страницу принудительно (`Cmd+Shift+R` на macOS). Это помогает, если браузер держит прежний HTML/скрипт, но не заменяет проверку процесса и порта.

Для обновления интерфейса удалять `meditron.db` вручную не нужно: версия страницы берётся из исходников Vite или веб-образа Docker. При стандартном повторном запуске `dev.sh` база очищается автоматически.

## Запуск через Docker Compose

При установленном Docker с Compose из корня проекта:

```bash
docker compose up --build --force-recreate
```

Интерфейс и API доступны по тем же стандартным адресам. Compose поднимает PostgreSQL, миграции, API, worker и веб-сервер. Команда с `--force-recreate` очищает данные приложения в выделенной демонстрационной базе PostgreSQL и добавляет новый набор пациентов; сам Docker volume сохраняется. Этот способ описан по конфигурации проекта; на текущей машине Docker отсутствует, поэтому фактический старт Compose здесь не проверен.

## Что посмотреть после запуска

В профиле «Специалист» карточки заявок показывают текст находки, чтобы различать случаи. Кнопка «Добавить исследование» позволяет создать новые примеры:

| Входное заключение | Проект до решения специалиста | Что увидит пациент после подтверждения |
| --- | --- | --- |
| КТ: 0 лёгочных узлов | Новый шаг не предложен | Явное сообщение, что по текущему заключению новый шаг не назначен; записи нет |
| КТ: 1 лёгочный узел | Консультация пульмонолога | Консультация и выбор времени |
| КТ: 3 лёгочных узла | Консультация пульмонолога | Консультация и выбор времени |
| КТ: 3 узла + пример анализа | Та же консультация модели; открывается редактор специалиста с анализом | После правки и подтверждения — консультация и отдельная запись на анализ; результат анализа нужен до выполнения основного шага |
| Маммография: BI-RADS 1/2, 3/2, 4/2 или 5/2 | Соответственно: без шага, обсуждение контроля, консультация или приоритетная консультация | Только утверждённый вариант |
| Маммография: отсутствует обязательное поле | Ручной выбор | Ничего до решения специалиста |

Пример с анализом **не означает**, что модель назначила исследование по числу узлов: это предзаполненная синтетическая правка специалиста для показа параллельной подготовки. Необходимость конкретного анализа в реальной клинике должна определяться её медицинским протоколом. Входные данные и рекомендации демо остаются гипотезами.

1. Выберите профиль «Специалист» в верхней панели, создайте синтетический случай маммографии с находкой и откройте его из списка заявок. На экране видны заключение, факты BI-RADS, проект маршрута и поля, повлиявшие на прогноз. Стрелка назад возвращает к списку.
2. Откройте кабинет пациента: проект ещё скрыт. Вернитесь к специалисту, при необходимости исправьте путь и подтвердите текущую версию.
3. После публикации пациент видит **один** утверждённый шаг и может запросить запись. При правке проекта специалист может добавить синтетический анализ как подготовку: пациент записывается на него и основной шаг, но результат основного шага принимается только после готовности анализа.
4. Зарегистрируйте результат основного шага «Требуется следующий шаг»: появится связанный ручной проект новой версии, который специалист должен заполнить и подтвердить. Для завершения цикла используйте результат `resolved`.
5. Попробуйте КТ с неизвестной целью исследования: маршрут передаётся на ручной разбор. Исправленное заключение создаёт новую версию и требует повторного решения.

## Проверка проекта

```bash
python3 scripts/validate_tag_catalog.py
bash scripts/check.sh
```

`check.sh` запускает проверку Python, конфигураций, тесты backend и сборку frontend. Браузерные end-to-end тесты запускаются отдельно; команды приведены в [README](../README.md#проверки). Проверка структуры каталога и успешная техническая сборка **не** заменяют медицинское утверждение направлений.
