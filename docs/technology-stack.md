# Технологический стек Patient pathway

**Статус:** выбран для реализации демонстрационного контура, 04.10.2026. Связанный план работ: [implementation-plan.md](implementation-plan.md). Точные версии зависимостей закрепляются lock-файлами при создании проекта и обновляются после проверки совместимости. Для пилота стек пересматривается по требованиям учреждения.

## Основное решение

**Фактическая реализация v0.1 (04.10.2026):** стек ниже реализуется в исполняемом синтетическом контуре. Для запуска без установленного Docker добавлен SQLite как локальный режим с сериализацией транзакций; целевая БД остаётся PostgreSQL. Состав реально подключённых компонентов и ограничения: [implementation-status.md](implementation-status.md).

Модульный backend на Python, один PostgreSQL, отдельный процесс фоновых задач из того же кодового проекта и веб-интерфейс React. Ядро маршрутизации зависит от канонических фактов, а не от Kafka, PACS или конкретной МИС. Адаптеры и профили учреждения подключаются на границе системы. Основной исполняемый результат — версионируемый условный маршрут с основаниями, подтверждением специалиста и доступным пациенту ближайшим шагом.

| Область | Выбор | Почему здесь подходит | Граница применения |
| --- | --- | --- | --- |
| Язык backend | Python 3.12, статическая типизация ключевого домена | Один язык для DICOM, парсера, модели и API; зрелая экосистема обработки медицинских форматов | Не использовать динамический `eval` для профилей полей |
| HTTP API | [FastAPI](https://fastapi.tiangolo.com/) | Удобно описывать типизированные запросы и ответы, получать OpenAPI для виджета и интеграций | API не содержит медицинскую логику; он вызывает доменные операции |
| Валидация входа и DTO | [Pydantic](https://pydantic.dev/docs/validation/latest/concepts/models/) | Проверка типов, диапазонов и структуры входных сообщений; явная каноническая модель | Проверка формы данных не доказывает медицинскую правильность заключения |
| База данных | [PostgreSQL](https://www.postgresql.org/docs/current/) | Транзакции, ограничения уникальности, версии маршрутов, аудит и outbox в одной базе | В демо один экземпляр; схема мигрирует вместе с кодом |
| Доступ к данным | [SQLAlchemy 2.x](https://docs.sqlalchemy.org/en/20/orm/) + [psycopg 3](https://www.psycopg.org/psycopg3/docs/) + [Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html) | Явные синхронные транзакции и контролируемые миграции для часто меняющейся модели маршрута; синхронный доступ проще отладить в первом контуре | Доменная модель не должна сводиться к ORM-моделям; асинхронный драйвер нужен лишь после измерения узкого места |
| DICOM SR | [pydicom](https://pydicom.github.io/pydicom/stable/tutorials/sr_basics.html) для чтения DICOM и обхода дерева; [highdicom](https://highdicom.readthedocs.io/en/stable/generalsr.html) для построения и проверки подходящих синтетических SR | SR представляет дерево content items с кодами, числовыми и текстовыми значениями; можно сохранять путь до исходного элемента | Не предполагать, что любой SR реализует TID 1500 или полностью состоит из кодированных полей |
| Модель следующего шага | [CatBoost](https://catboost.ai/docs/en/concepts/algorithm-main-stages) поверх нормализованных полей SR | Поддерживает числовые и категориальные признаки и их сочетания; текущий артефакт обучен на синтетическом учителе | Независимая клиническая эффективность не доказана; отсутствие данных или неустойчивый выбор ведут к решению специалиста |
| Фоновые действия | Outbox в PostgreSQL + отдельный worker того же backend | Публикация пути, уведомления и запрос записи запускаются после коммита решения и повторяются идемпотентно | При росте нагрузки можно добавить брокер без изменения домена |
| Веб-интерфейс | [React](https://react.dev/learn/typescript) + TypeScript + [Vite](https://vite.dev/guide/) | Один набор компонентов для экрана специалиста, пациента и демо; быстрое локальное развитие, строгие типы API | Для внедрения виджет встраивается в интерфейс клиники или предоставляется API; демо-оболочка не является отдельным продуктом |
| Стили | CSS variables и дизайн-токены учреждения | Быстрая адаптация к основному сайту без переписывания UI | Названия услуг, тексты и разрешённые действия остаются настройкой учреждения |
| Локальный запуск | [Docker Compose](https://docs.docker.com/compose/) | Воспроизводимый запуск frontend, API, worker и PostgreSQL одной командой | Не считать Compose схемой промышленного размещения каждой клиники |
| Зависимости | [uv](https://docs.astral.sh/uv/guides/projects/) и `uv.lock` для Python; npm и `package-lock.json` для frontend | Одинаковые проверенные версии на машинах команды и в CI | Lock-файлы хранить в репозитории и обновлять осознанно |
| Качество | [pytest](https://docs.pytest.org/), [Playwright](https://playwright.dev/docs/intro), [Ruff](https://docs.astral.sh/ruff/) | Проверки инвариантов маршрута, двух форматов входа и сквозного пользовательского сценария; единый стиль Python | Не подменять экспертную проверку медицинских правил техническими тестами |

## Интеграционные адаптеры по этапам

1. **Первый работающий путь:** HTTP/файл с синтетическим JSON по БФТ и `.dcm` SR. Это позволяет проверить извлечение фактов и сравнить два представления без инфраструктурного шума.
2. **Демонстрация двух профилей:** Kafka consumer для JSON и симулятор PACS/SR. В Compose можно добавить тестовый Kafka broker и [Orthanc](https://orthanc.uclouvain.be/book/users/docker.html) как отдельный профиль. Это проверяет протокол обмена в тестовом окружении, но не совместимость с PACS заказчика.
3. **Подключение учреждения:** адаптеры МИС, каталога услуг, записи, кабинета и уведомлений разрабатываются по реальным контрактам клиники. Неизвестный протокол требует нового адаптера; отличие пути поля в известном формате решается профилем сопоставления.

Общий интерфейс входа возвращает `CanonicalReport`. Он содержит `study_uid`, техническую ссылку на приём, версию источника, модальность, `exam_purpose` и факты со ссылками на элементы исходного заключения. Прямые идентификаторы пациента не нужны аналитике; контур клиники отвечает за связь с пациентом и доставку в кабинет.

## Сознательно не включено в первую версию

| Технология | Причина решения | Когда вернуться |
| --- | --- | --- |
| Собственная NLP/LLM-модель | БФТ описывает ожидаемые поля, а реальных размеченных заключений нет; на синтетике нельзя убедительно доказать качество модели | Если появится корпус фактических отчётов и измеримая доля значимых свободных формулировок |
| Микросервисы и Kubernetes | Нет независимых команд, нагрузки и контрактов, ради которых оправдана распределённая сложность | После нескольких реальных внедрений и измерения узких мест |
| Temporal/Camunda | Для первой версии достаточно ограниченного графа шагов, явных статусов и транзакционных переходов | Если маршруты станут длинными, многомесячными и существенно изменяемыми учреждением |
| Универсальный конструктор медицинских правил для IT-службы | Техническое сопоставление полей и клиническое правило имеют разные права изменения | После утверждения процесса медицинского управления правилами |
| Прогноз конверсии или «uplift» на синтетике | Синтетические события проверяют расчёт метрики, но не измеряют поведение пациентов | При пилоте с контрольной группой и доступом к событиям оказания услуг |

## Размещение и данные

Для демо используются только синтетические случаи, локальные секреты и фиктивные контакты. Для пилота: размещение в согласованном контуре учреждения, TLS, авторизация через его механизм, отдельные роли специалиста и пациента, аудит доступа и решений, резервное копирование и политика хранения данных. Профиль учреждения, модель и сопоставление услуг версионируются отдельно. На каждом шаге перехода сохраняются исходная версия заключения, версия модели и принятая специалистом версия маршрута. Подробности — в [model-routing.md](model-routing.md).
