# Настройка профиля учреждения

Профиль — JSON-сопоставление технических полей заключения и кодов услуг. Он находится в `config/profiles.json`. Маршрут вычисляется из **канонических фактов**, поэтому смена пути или кода SR в профиле не требует править `backend/app/domain/routing.py`. Медицинские гипотезы хранятся отдельно в `config/rules.json` и требуют экспертного утверждения до клинического применения.

## Порядок подключения

1. Скопировать пример `private` для JSON или `pacs` для DICOM SR под новым ID профиля. `clinic_id` обозначает учреждение: несколько профилей источника могут иметь один `clinic_id`. Задать понятный `label` и `version`; `label` служит названием клиники в демоинтерфейсе и должен совпадать у всех её профилей. После появления заключений нельзя переносить тот же ID профиля в другую клинику — вход будет отклонён. Для нового профиля установить `demo_scenarios: false`: встроенный генератор знает только прилагаемые синтетические схемы.
2. Выбрать `input`: `json` или `dicom`. Сопоставить `study_path`, `conclusion_path` и `fields.<modality>.<canonical_code>.path` для JSON. Обычный путь состоит из имён полей через точку, например `aiResult.probParams.mmg.mmg_rads_right`. Для массива можно указать числовой индекс (`reports[0].conclusion`) или выбрать объект по строковому коду (`findings[code=right].value`). Результат фильтра должен быть единственным; дубликат вызывает ошибку при разборе. Источником факта сохраняется фактический индекс найденного элемента, например `findings[1].value`. Произвольные JSONPath-выражения не выполняются.
3. Для SR задать `sr_scheme`, `sr_conclusion_code` и `sr_code` каждого факта. Демопрофиль читает локальные коды `ZDEMO`; коды промышленного поставщика требуется получить из его файлов и документации. `path` остаётся обязательным полем профиля, но SR-парсер использует `sr_code`.
4. У каждого факта указать `type`, `min`, `max` и при необходимости `unit`. Два разных факта одной модальности не должны читать один путь или один код SR. Неподходящий тип и единица измерения отвергаются, не преобразуются молча.
5. Настроить `services`: соответствие `action_type` шага локальному коду услуги. `booking_mode` выбирает `local_simulator` или `deferred_simulator` только для синтетического контура. Для последнего нужен `booking_callback` с именем переменной окружения секрета, а не самим секретом. Если используется предварительный подписанный HTTP-вход заключений, добавить `report_ingress` с отдельным именем переменной секрета. Для иных будущих транспортов блок может отсутствовать; [контракт подписанного входа](report-ingress-contract.md).
6. Проверить черновую конфигурацию и пример входа, повысить `version` при изменении сопоставления, затем опубликовать проверенный набор командой ниже. Новый релиз применяется к новым запросам в локальном процессе; уже принятые заключения сохраняют прежний снимок. В контейнерном развёртывании релиз поставляется в образе и требует его обновления.

`input` и `booking_mode` выбираются независимо: тестами пройдены все четыре сочетания JSON/SR и немедленной/отложенной демозаписи. Публикация нового профиля действует на **новые версии заключений**. У опубликованного маршрута коды услуг и режим записи берутся из его сохранённого снимка, поэтому изменение файла не перенастраивает уже показанный пациенту путь. При согласовании старой записи с новой версией код услуги сравнивается со снимком **новой** версии. Для ещё ожидающих внешнего ответа записей сохраняйте доступность секретов обратного статуса, указанных в старых снимках, до завершения этих запросов.

Текущий контракт правила допускает **ноль или один** клинический шаг. Ключ `action_type` шага и каждый `service_key` лабораторной подготовки должны иметь сопоставление в `profiles[].services` для используемой клиники. Раздел `prerequisites` содержит до трёх задач `kind: lab` с уникальными `key` и условием `before_booking` либо `before_execution`. В опубликованном демонстрационном профиле `lab_demo` обозначает только вымышленную услугу; реальные анализы и правила подготовки утверждает учреждение. Подробная модель: [next-step-cycle.md](next-step-cycle.md).

Для нескольких источников одной клиники создайте отдельные профили с общим `clinic_id`. Случай определяется парой `clinic_id + study_uid`; каждая версия заключения хранит свой `profile_id`, а поле `profile_id` у случая показывает последний принятый источник. **Номера `source_version` должны согласованно возрастать для данного исследования через все источники.** Совпавшие версия, текст заключения и типизированные факты считаются дублем независимо от JSON-пути или SR-узла. При расхождении содержания в той же версии возвращается 409, а исправление требует новой версии и повторного решения специалиста. Пациентский токен и история маршрута при смене источника сохраняются. Слоты резервируются в области клиники, поэтому профили одной клиники должны сопоставлять одинаковые услуги с согласованными кодами каталога.

```bash
PYTHONPATH=backend .venv/bin/python -m app.config_check
bash scripts/check.sh
```

Проверка выявляет ошибки схемы, повторные коды, отсутствующие обязательные факты, ссылки правил на несуществующие факты и циклы маршрута. Она проверяет и черновики `profiles.json`/`rules.json`, и активный релиз. После проверки и предпросмотра синтетического входа опубликуйте оба файла одной операцией:

```bash
PYTHONPATH=backend .venv/bin/python -m app.config_publish --author clinic-it --reason "Обновление сопоставления полей"
```

Команда сохраняет неизменяемую копию с автором, причиной и временем в `config/releases/`, затем атомарно заменяет небольшой `config/active-release.json` с ID и контрольной суммой. Запрос читает указатель один раз и использует одну проверенную пару до сохранения маршрута; ID релиза сохраняется в исходном отчёте вместе со снимком. Правка черновиков не влияет на работающий контур до публикации. При отсутствии активного указателя разрешён прежний режим чтения черновиков для тестов и первичной настройки; в подготовленном проекте указатель уже есть. Это файловый журнал оператора, а не промышленный механизм разграничения полномочий или медицинского утверждения правил.

## Предпросмотр без сохранения случая

Оба адреса возвращают `CanonicalReport`, `profile_version` и `route_preview` со статусом, шагами, предупреждениями и trace. Они не создают `Case` и запись в БД.

```bash
curl -sS -X POST http://127.0.0.1:8000/api/v1/profiles/private/preview \
  -H 'X-Demo-Role: reviewer' -H 'Content-Type: application/json' \
  --data-binary @fixtures/bft-json/mmg-finding.json
```

```bash
curl -sS -X POST 'http://127.0.0.1:8000/api/v1/profiles/pacs/preview-sr?modality=MAMMOGRAPHY&encounter_ref=example&source_version=1&exam_purpose=diagnostic' \
  -H 'X-Demo-Role: reviewer' \
  -F 'file=@fixtures/dicom-sr/mmg-finding.dcm;type=application/dicom'
```

Синтетический генератор «Новое исследование» показывает только профили с `demo_scenarios: true` и создаёт входы по прилагаемым примерам. Для нового профиля с другими путями используйте предпросмотр собственного **синтетического** JSON/SR и соответствующий endpoint приёма. Требование `synthetic=true` для JSON и `PatientID=SYNTHETIC` для SR оставлено на весь демонстрационный контур.

Если производитель отдаёт факты массивом объектов, профиль может указать пути `aiResult.findings[code=right].value` и `aiResult.findings[code=left].value`. Порядок элементов тогда не влияет на маршрут. Фильтр сравнивает строковый код точно, без преобразования типов. Отсутствующий элемент приводит к отсутствующему факту и ручному решению, когда факт обязателен для правила; несколько совпадений отклоняются как неоднозначный вход. Индекс `[0]` используйте лишь там, где порядок элементов закреплён контрактом источника.

## Границы v0.1

- Правила `HYPOTHESIS` не являются утверждённой медицинской матрицей. Технический профиль нельзя использовать для изменения медицинского смысла шагов.
- Предпросмотр SR работает с однозначными NUM/TEXT-узлами указанной схемы. JSON-селекторы поддерживают один элемент по индексу или точному строковому коду, но не агрегируют повторные находки. Произвольный SR и текст без согласованного шаблона не угадываются.
- Редактора профиля в интерфейсе нет; файл может подготовить IT-служба клиники и проверить командой или API. CLI сохраняет автора и причину публикации, но права оператора, подпись релиза и его медицинское утверждение требуют отдельного процесса.
- Реальные источники Kafka/PACS, каталог и сервис записи требуют согласованных контрактов и отдельных транспортных адаптеров.
- Один профиль выбирает один формат входа; несколько профилей с общим `clinic_id` объединяют свои версии по `study_uid`. Реальные правила сопоставления UID, версий и каталога услуг должны быть проверены на контрактах учреждения. Между разными клиниками случаи не объединяются.
