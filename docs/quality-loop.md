# Как использовать правки специалиста

Статус: синтетический контур, обновлено 05.10.2026. Правки маршрута — источник обратной связи о **кандидатах модели следующего шага** и формулировках. Они не доказывают ошибку диагностического заключения ИИ и не обновляют действующий артефакт автоматически. Актуальный план пакетного улучшения — в [model-routing.md](model-routing.md); ниже сохранён исторический процесс для первого движка правил.

## Данные одного решения

`clinical_decisions` хранит исходные и окончательные шаги, действие, свободное обоснование и категорию причины. Для новых решений демоинтерфейс просит выбрать категорию; API принимает её необязательной для совместимости с прежними клиентами. Отсутствие попадает в `unspecified`.

| Код | Когда выбирать |
| --- | --- |
| `insufficient_context` | Для уверенного пути не хватает доступных полей или назначения исследования. |
| `route_logic` | Специалист меняет набор шагов, действие или условие перехода. |
| `service_mapping` | Предложенное действие нельзя однозначно сопоставить с услугой учреждения. |
| `wording` | Шаг остаётся тем же, меняется понятность текста. |
| `other` | Причина не попадает в перечисленные категории; пояснение обязательно. |

Категория не заменяет свободный комментарий в журнале решения. При `approve` категория в БД — `none`, при старой правке без кода — `unspecified`.

## Доступная аналитика

`GET /api/v1/quality/rule-review` группирует **принятые решения**, а не всех пациентов, по профилю учреждения, модальности, назначению исследования (`screening`, `diagnostic`, `unknown`), версии набора правил, ID совпавшего правила и режиму проекта (`rule`/`manual`). В каждой группе есть количество утверждений без правки, правок и отклонений, разбивка категорий причин и тип правки:

- `wording_only`: ключи шагов, действия и условия прежние, меняется только представление;
- `route_changed`: изменились шаги, действия, порядок или условия;
- `no_effect`: команда правки не изменила шаги.

Ответ содержит только агрегаты. Он не возвращает `case_id`, `study_uid`, токен, текст заключения, точные значения фактов, указатели на поля или свободный комментарий. Доступ ограничен деморолью специалиста. **Для реальных данных этого недостаточно как меры обезличивания**: до эксплуатации нужны права по учреждению и подавление малых групп, чтобы единичные случаи нельзя было восстановить из контекста.

## Контур улучшения правил

1. По числу решений и доле `route_changed`/`rejected` выбрать группы для разбора. Малое число случаев трактовать как сигнал к просмотру, не как статистическое доказательство.
2. Уполномоченный специалист просматривает конкретные решения внутри защищённого контура учреждения, включая исходное заключение и основания. Агрегированный API не предназначен для такого просмотра.
3. Если причина систематическая, сформулировать изменение матрицы, области применимости, шаблона текста или технического профиля. Не смешивать настройку полей с медицинским правилом.
4. Утвердить медицинское изменение, выпустить новую версию `config/rules.json` и отдельные сценарии проверки. Технические изменения профиля выпускать со своей версией. Уже принятые решения и снимки конфигурации не переписывать.
5. Проверить новую версию на фиксированном наборе синтетических случаев и затем на обезличенных локальных примерах учреждения. Измерить частоту ручных решений и правок по одинаковым когортам. Публиковать в рабочем контуре только после медицинского и интеграционного согласования.

Нельзя использовать поправки как разметку для автоматического обучения без отдельного протокола качества данных, прав на использование и независимой клинической проверки. В текущей версии нет ни обучения, ни автоматического применения новых правил.
