# Контракт обратного статуса записи и отмены v0.2

Это наш предлагаемый HTTP-контракт для подключаемого сервиса записи. Он работает в синтетическом контуре, но не проверен с МИС или PACS конкретной клиники. Демо-кнопки используют отдельный адрес `/api/v1/demo/bookings/{booking_id}/feedback` и не являются доверенным внешним каналом.

## Запрос

`POST /api/v1/integrations/bookings/{booking_id}/feedback`

Заголовки:

| Заголовок | Значение |
| --- | --- |
| `Content-Type` | `application/json` |
| `X-Source-Profile` | ID настроенного профиля, сейчас `pacs` |
| `X-Event-Id` | Уникальный у источника ID события, 1–128 символов из `[A-Za-z0-9._:-]` |
| `X-Timestamp` | Текущее Unix-время в секундах, десятичное ASCII |
| `X-Signature` | Нижний шестнадцатеричный HMAC-SHA256, 64 символа |

Тело:

```json
{
  "case_id": "UUID случая, полученный при запросе записи",
  "profile_id": "pacs",
  "external_ref": "REQ-<booking UUID>",
  "status": "confirmed",
  "reason": ""
}
```

Для ожидающей записи (`awaiting_confirmation`) допустимы `confirmed`, `rejected` и `no_slots`; для двух последних требуется непустой `reason` до 500 символов. Для запрошенной отмены (`cancel_requested`) допустимы `cancelled` и `cancel_rejected`; отказ в отмене требует причины. Ответ `cancelled` освобождает локальный слот, `cancel_rejected` возвращает запись в `confirmed` и сохраняет причину. Ответ из другой группы состояний отклоняется. `booking_id` — наш ID из ответа записи; `external_ref` — корреляционный ID, сохранённый в записи. Оба должны совпасть. Тело с лишними полями отклоняется.

Пациентский запрос отмены для отложенного профиля фиксирует `cancel_requested` и ставит демонстрационную передачу отмены в outbox. До подтверждения клиникой локальный слот остаётся занятым и повторная запись на шаг блокируется. Для локального симулятора отмена происходит сразу. Реальной исходящей передачи отмены в клинику пока нет: этот переход проверяет внутренний контракт и обратный статус, а не готовность интеграции.

## Подпись

Для профиля `pacs` сервер читает секрет из `MEDITRON_BOOKING_SECRET_PACS`. Имя переменной задаётся в `config/profiles.json`, сам секрет хранится только в окружении. При отсутствии секрета вход отвечает 503. Для промышленной среды секрет должен быть создан и передан средствами управления секретами учреждения.

Подписываются **исходные байты JSON-тела**, без повторной сериализации. Сообщение для HMAC — последовательность байтов UTF-8:

```text
X-Timestamp + "\n" + X-Source-Profile + "\n" + X-Event-Id + "\n" + HTTP path + "\n" + raw body
```

`HTTP path` начинается с `/api/v1/integrations/...`, без домена и query-параметров. Подпись вычисляется как `hex(HMAC_SHA256(secret, message))`. Сервер сравнивает её за постоянное время. Допустимое расхождение часов — 300 секунд в обе стороны.

По `booking_id` сервер находит профиль источника и его снимок, сохранённые с исходной версией маршрута. Если новый отчёт пришёл через другой профиль той же клиники, поздний ответ всё равно проверяется по исходному профилю записи. Он проверяет подпись **до разбора JSON-тела** по настройкам этого снимка; смена действующего файла профилей не меняет правила проверки уже ожидающей записи. После проверки подписи сервер сверяет профиль, случай, внешний идентификатор и допустимый переход `awaiting_confirmation → confirmed/rejected/no_slots`. Успешная запись статуса и событие воронки выполняются в одной транзакции. Повтор события с тем же `X-Event-Id` и телом возвращает прежний ответ; повтор ID с другим содержимым даёт 409. ID уникален для профиля, включая разные записи. Ответы с неподходящей подписью, временем или профилем не меняют состояние. Размер тела ограничен 16 КБ на уровне приложения.

## Что ещё должен согласовать интегратор

- Формат реальных исходящих запросов записи и отмены и момент передачи после коммита. Сейчас outbox отмечает только демонстрационную передачу; сетевой вызов отсутствует.
- Защищённый канал и аутентификацию фактических Kafka/PACS-коннекторов. Для синтетического HTTP-входа заключений теперь есть отдельный [предварительный HMAC-контракт](report-ingress-contract.md); подпись в этом документе относится только к обратному статусу записи.
- Как обрабатывать изменение времени, поздние противоречивые ответы и состояние внешней системы после сбоя. Локальное согласование старой записи с новым маршрутом поддержано при совпадении шага и услуги; слот и `external_ref` не меняются, поздний ответ учитывается на согласованной версии. Каждый запрос записи или отмены принимает один терминальный ответ; повтор того же события дедуплицируется.
- Ротацию секрета и допустимое расхождение времени. В v0.1 снимок профиля хранит имя переменной окружения с одним секретом; старое имя и секрет должны оставаться доступными до получения ответов по ожидающим записям.
