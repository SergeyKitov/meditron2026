# Как оценивать разбор заключений и построение маршрута

Дата: 04.10.2026. Это протокол оценки **нашего контура обработки и маршрутизации**, а не проверки медицинской правильности ИИ-заключения. Текущая исполняемая часть использует семь синтетических сценариев, каждый в JSON и DICOM SR. Правила и ожидаемые пути имеют статус `HYPOTHESIS`.

## Зачем несколько метрик

Единственная F1 скрыла бы важные типы ошибок. Например, система могла бы верно извлечь все поля, но предложить маршрут, когда данных для него недостаточно. Для пациента и специалиста это иной сбой, чем пропуск одного поля. Поэтому оценка разделена на четыре уровня:

| Уровень | Что сравниваем | Почему это нужно |
| --- | --- | --- |
| Извлечение | Наборы `(код, значение, единица)` из заключения и независимой ожидаемой разметки; указатель на поле не сравнивается между JSON и SR | Выявляет пропущенные, лишние и неверно прочитанные факты. |
| Решение о ручном разборе | Ожидаемый `manual` против фактического `draft` и наоборот | `unsafe_auto_routes` показывает, когда правило сработало там, где эталон требует человека. |
| Структура ближайшего шага | Статус, единственный ключ действия, тип услуги и основание; отдельно задачи подготовки и их условия | Верное название действия не доказывает верную готовность к записи и выполнению. |
| Переносимость формата | Результат JSON против эквивалентного SR одного синтетического случая | Показывает, изменил ли технический формат доменное решение. |

Для извлечения и ключей шагов считаются `TP`, `FP`, `FN`, затем `precision = TP/(TP+FP)`, `recall = TP/(TP+FN)` и `F1 = 2PR/(P+R)`. Когда знаменатель метрики отсутствует, она равна `null`, а не автоматически `1`. При наличии ожидаемого элемента и полном пропуске F1 равна `0`. Метрика шагов считается только на случаях, где ожидается проект `draft`: пустой маршрут при `manual` не должен искусственно улучшать F1.

Отдельно выводятся доля точных совпадений и оба направления ошибки воздержания. Это позволяет увидеть, например, что высокая F1 по шагам сосуществует с лишними автоматическими решениями. Для условного маршрута точное совпадение его контракта важнее одной F1 по названиям услуг.

## Исполняемый синтетический прогон

Из корня проекта:

```bash
PYTHONPATH=backend .venv/bin/python scripts/evaluate_fixtures.py
```

Команда читает опубликованную пару профилей и правил, затем файлы `fixtures/bft-json`, `fixtures/dicom-sr` и `fixtures/expected`. Она требует одинаковый непустой набор имён во всех трёх каталогах, печатает JSON-отчёт с разбивкой по модальности и назначению исследования и возвращает ненулевой код при расхождении с ожидаемым или между форматами. Ожидаемые факты и контракт шагов заданы явно в фикстурах; они не вычисляются из текущих правил. Скрипт генерации фикстур хранит их исходную спецификацию.

Сохранённый [машинный отчёт](evaluation-results-synthetic.json) привязан к ID опубликованного релиза конфигурации и версии правил. Сейчас прогон даёт 7 совпавших пар форматов, 14 точных разборов и маршрутов, 0 лишних автоматических маршрутов на 4 представлениях двух ручных сценариев. Эти числа доказывают лишь соответствие **узкому синтетическому набору**. JSON и SR одного сценария — две проверки интеграции, а не два независимых пациента. Значение `1.0` для F1 здесь нельзя представлять как клиническую точность, пригодность для промышленного SR или достаточность данных.

## Переход к настоящей оценке

До пилота требуются реальные обезличенные образцы схем учреждения и независимая экспертная разметка ожидаемых полей, допустимости автоматического проекта, шагов и условий. Спорные случаи должны получать согласованное экспертное решение. Выборку нужно разделить минимум по модальности, назначению исследования, формату источника и сценариям отсутствующих/противоречивых данных; иначе общая средняя скроет провал одной ветки. Версии профиля и правил, критерии включения и вся разметка должны быть зафиксированы **до** оценки; обучающие или настроечные случаи отделяются от независимой проверки.

Для решения о достаточности данных одной F1 недостаточно. Нужно заранее выбрать допустимую частоту каждого типа ошибки и доверительную неопределённость **по важным подгруппам**, согласовать пороги с медицинскими экспертами и учреждением и только затем рассчитывать требуемый объём выборки. Даже отсутствие опасных ошибок в небольшой выборке не доказывает их отсутствие в эксплуатации. После подтверждения маршрута в рабочем процессе отдельно измеряются доля правок специалиста, задержка от готовности SR до решения и конверсия показа в подтверждённую запись; для оценки uplift нужна контрольная группа.

Ни один из этих показателей не заменяет обязательное решение специалиста перед публикацией пациенту.
