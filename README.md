# Patient pathway

Сервис предлагает **один следующий шаг** по уже сформированному ИИ-заключению во время текущего приёма. После решения специалиста этот шаг показывается пациенту и становится доступным для записи. После получения результата сервис создаёт связанную новую версию для следующего решения; так формируется повторяемый путь. Если услуге нужна подготовка, анализы можно организовать параллельно с основным шагом при заданных условиях.

**Новая модель:** [один шаг, повторяемый цикл и параллельные анализы](docs/next-step-cycle.md), включая диаграммы, условия и границы реализации.

**Актуальная архитектура:** [docs/architecture.md](docs/architecture.md). В документе зафиксированы границы продукта, поток данных, варианты подключения клиники, настройка полей, диаграммы Mermaid и вопросы перед пилотом.

**План демонстрации:** [docs/synthetic-demo-and-contracts.md](docs/synthetic-demo-and-contracts.md). Две условные клиники с разными источниками результата используют одно ядро маршрутизации. Все входные данные и медицинские сценарии демо синтетические.

**Разработка:** [план реализации](docs/implementation-plan.md) от фикстур до сквозного демо; [выбранный стек и обоснование](docs/technology-stack.md).

**Запуск:** [пошаговая инструкция для локального демо и Docker Compose](docs/run.md). **Направления:** [короткий каталог причин и специалистов](docs/tag-catalog.md) для обсуждения с медицинским экспертом.

**Для защиты:** [проверка комплекта по требованиям оформления](docs/submission-checklist.md) и [актуальные материалы питча](docs/pitch/README.md).

**Модель и обратная связь:** [CatBoost, источники данных и выпуск следующей версии](docs/model-routing.md). Правка действует сразу для конкретного пациента; пакетное переобучение после экспертной разметки пока запланировано. В демо доступна сводка без идентификаторов и текста заключений.

**Оценка маршрутизатора:** [метрики и границы синтетической проверки](docs/evaluation-protocol.md). Отдельная команда сравнивает ожидаемые факты, условия шагов и решение о ручном разборе для JSON/SR: `PYTHONPATH=backend .venv/bin/python scripts/evaluate_fixtures.py`.

**Вход заключений:** помимо ручных демо-endpoint есть [предварительный подписанный HTTP-контракт JSON/SR](docs/report-ingress-contract.md) для синтетической проверки источника и повторов сообщений. Он не заменяет реальный Kafka/PACS-адаптер.

**Текущее состояние: исполняемый синтетический контур v0.1.** Работают получение JSON/SR, CatBoost-проект **одного** шага по нормализованным полям, правка и подтверждение специалистом, публикация, кабинет пациента, отказ с причиной и возврат к записи, симуляция записи с немедленным или отложенным ответом, параллельная лабораторная подготовка и новая связанная версия после результата шага. В верхней панели есть три демонстрационных профиля: «Специалист», «Пациент», «Администратор». [Что реализовано, API, диаграммы и ограничения](docs/implementation-status.md).

**Сценарии для показа:** КТ без узлов, с одним или тремя узлами; маммография BI-RADS 1–5 и неполное заключение. Отдельный пример КТ открывает редактор, где специалист добавляет синтетический анализ к консультации. [Ожидаемый путь каждого примера](docs/run.md#что-посмотреть-после-запуска).

В интерфейсе администратора журнал связывает каждое исследование с устойчивым обезличенным обозначением `P-…`, производным от идентификатора случая. В кабинете пациента показывается только его выбранный случай без общего журнала. Обозначение пока не связывает несколько исследований одного человека в общую историю.

Воронка показывает конверсию в подтверждённую запись и отдельный обзор явных отказов и возвратов по шагам после показа маршрута. На синтетике это проверяет логику продукта, а не доказывает эффект в клинике.

## Быстрый запуск без Docker

Из корня проекта нужны Python 3.12 или 3.13, `uv`, Node.js 20.18+ и npm.

```bash
uv sync --frozen
npm --prefix frontend ci
bash scripts/dev.sh
```

Открыть **http://127.0.0.1:5173**. API: **http://127.0.0.1:8000/docs**.

Для стандартной локальной базы `meditron.db` скрипт при каждом запуске удаляет предыдущие случаи, применяет миграции, добавляет девять новых вымышленных пациентов и запускает API, worker и Vite. Чтобы сохранить текущую базу для отладки, запустите `MEDITRON_DEMO_RESET=0 bash scripts/dev.sh`. База, указанная через другой `DATABASE_URL`, автоматически не очищается. `Ctrl+C` завершает процессы. SQLite — локальный режим демонстрации; целевое хранение — PostgreSQL.

Если после запуска виден прежний интерфейс, проверьте каталог проекта и занятые порты. Новый скрипт сообщает об уже работающем сервере и печатает адрес только после проверки страницы **Patient pathway**. Пошаговая диагностика и обновление Docker-образа — в [инструкции запуска](docs/run.md#если-открывается-прежний-вариант).

## Запуск с PostgreSQL

```bash
docker compose up --build --force-recreate
```

Те же адреса; PostgreSQL хранится в Docker volume. Команда с `--force-recreate` заново запускает миграцию, очищает случаи и добавляет новый набор пациентов. Для первой версии используется демонстрационный пароль из `.env.example`. Compose подготовлен, но пока не проверен на этой машине — Docker здесь отсутствует. Контур предназначен для локальных синтетических данных; внешние API и промышленная авторизация ещё не подключены.

## Как показать идею

1. Переключитесь на профиль «Специалист», выберите заявку на маммографию: видны заключение, поля BI-RADS и проект пути. Раскройте «Основания решения». Стрелка назад возвращает к списку заявок.
2. Откройте кабинет пациента до подтверждения: проект скрыт.
3. Вернитесь к специалисту, измените название шага и укажите причину; сохраните и подтвердите.
   Альтернативный сценарий: отклоните проект с причиной, откройте автоматически созданную ручную версию, исправьте её и подтвердите. Новая версия пути не показывается пациенту до подтверждения.
4. В кабинете пациента сначала откажитесь от доступного шага с причиной: специалист увидит этот выбор. Затем вернитесь к записи, выберите слот и запишитесь. При необходимости добавьте анализ в редакторе маршрута; основной шаг можно записать параллельно, но выполнить только после принятого результата анализа.
5. На экране специалиста загрузите синтетический результат «Требуется следующий шаг». Появится связанный ручной проект **одного нового шага**; задайте его и подтвердите, чтобы пациент увидел продолжение.
6. Добавьте КТ через DICOM SR с неизвестным назначением: автоматическое подтверждение заблокировано, требуется ручное решение.
7. Получите исправленное заключение: новая запись приостановлена до повторного подтверждения; история версий сохранена.
8. Для профиля «Диагностический центр · DICOM SR» выберите запись: пациент увидит ожидание подтверждения. На экране специалиста в блоке симулятора подтвердите слот или откажите с причиной; только подтверждённый ответ попадёт в воронку записи. После подтверждения попросите отмену в кабинете пациента: слот останется занятым до отдельного ответа системы записи.

Все предложения модели имеют статус **HYPOTHESIS**. Анализы в демо выбирает специалист, а не парсер SR. Запись и уведомления симулируются. Переключение профилей служит только демонстрации и не обеспечивает реальные права доступа. Реальные интеграционные контракты и клинические метки пока не утверждены.

## Входы, выходы и границы

Входом служит структурированное текстовое заключение ИИ в BFT-подобном JSON либо DICOM SR. Профиль учреждения сопоставляет известные поля и коды каноническим фактам. Выходы: проект одного шага с основаниями, решение специалиста, опубликованная версия для кабинета пациента, задачи подготовки, события записи и воронки. Основные HTTP-методы документированы в `/docs`, вход заключений — в [контракте источника](docs/report-ingress-contract.md), обратные статусы записи — в [контракте записи](docs/booking-feedback-contract.md). Фикстуры лежат в `fixtures/`.

Сервис не проверяет диагноз и не анализирует изображения. Он не использует возраст, жалобы или анамнез; при недостатке данных переводит выбор на специалиста. Демо не является системой клинических назначений и не доказывает медицинскую безопасность или рост конверсии. История нескольких исследований с разными `study_uid` пока не связывается в один продольный путь.

Для обратного статуса записи предусмотрен [подписанный интеграционный контракт](docs/booking-feedback-contract.md). Он требует секрет в окружении; демо-кнопки работают без него и не имитируют промышленную аутентификацию.

## Проверки

```bash
bash scripts/check.sh
# Если локальное демо уже запущено на стандартных портах, используйте отдельные порты для тестов.
npm --prefix frontend exec -- playwright install chromium
MEDITRON_API_PORT=8100 MEDITRON_WEB_PORT=5183 npm --prefix frontend run test:e2e
```

Браузерные тесты сохраняют снимки в `frontend/test-results/`. Зависимости зафиксированы в `uv.lock` и `frontend/package-lock.json`.

## Где менять поведение

- `config/profiles.json` — черновик путей полей, кодов SR и услуг клиники; после проверки публикуется вместе с правилами через `python -m app.config_publish --author ... --reason ...`.
- [Инструкция настройки и предпросмотра профиля](docs/configuration-guide.md) — для IT-службы учреждения.
- `config/rules.json` — черновик демонстрационной матрицы правил; активный набор указан в `config/active-release.json`.
- `backend/app/domain/` — независимое ядро маршрутизации.
- `backend/app/application/` — транзакции, версии, публикация, запись.
- `backend/app/adapters/` — преобразование входов и генератор синтетических данных.
- `frontend/src/` — рабочие экраны демо.
- `fixtures/` — семь пар JSON/SR и ожидаемые результаты.

Повторно создать фикстуры: `PYTHONPATH=backend .venv/bin/python scripts/generate_fixtures.py`. Это заменит сгенерированные `.dcm` и JSON в `fixtures/`.
